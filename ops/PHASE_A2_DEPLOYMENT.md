# Phase A-2 本番変更記録（2026-11-23）

## 適用済み（Supabase）

1. 非公開スキーマ `hq_private` に、`habit_states` の全行と変更前 `save_habit_state` の定義をバックアップ。
2. バックアップは**本番記録1行と完全一致**、元のrevision=23、テーブルRLS有効。anon/authenticated はスキーマ使用権限もテーブル読み取り権限もないことを確認。
3. `save_habit_state` のUPDATE条件に「現行データが `habitSchemaVersion:2` の場合、送信データもv2であること」を追加。関数シグネチャ・認証チェック・revision・サイズ・画像禁止ルールは維持。
4. DBトランザクション内で既存記録を一時的にv2にしてRPCを検証し、最後に `ROLLBACK`。次のケースを確認：
   - v1→v2の初回保存成功
   - v2保存後のv1からの上書きを拒否
   - v2→v2保存成功
   - revision不一致を拒否
   - 未認証書き込み拒否
   - 300KB超の書き込み拒否
   - Base64画像を含む状態の書き込み拒否
5. ロールバック後、**習慣データとrevisionがバックアップと完全一致**。本番ユーザー記録への恒久的なテスト書き込みなし。

ソース：`ops/phase-a2-rpc-guard.sql`  
緊急時のみ：`ops/phase-a2-rollback.sql`

## 重要な制限

- このRPC保護は、**旧クライアントが公開RPCで保存する場合**を保護する。ユーザー自身が直接テーブルUPDATEする特殊な経路までは保護対象にしていない。
- 古いタブで発生した未同期のチェックは上書き拒否によりクラウドへ送信できなくなる可能性がある。古い端末の記録を先にバックアップする案内が必要。
- アプリのv2が初めて保存されるまでは、既存JSONBは旧形式なので通常どおり旧クライアントによる保存が可能（既存記録への影響を抑えるため）。新形式へ移行後に保護が始まる。
- 本番PC⇄スマホ両方向の実ユーザー同期・iOS実機表示・Oura実同期は、GitHub CIテストとは区別して確認する。
